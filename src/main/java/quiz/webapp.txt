Web port of quiz.QuizFactory — architecture summary
=====================================================

Current state
-------------
Quiz extends Thread and builds Swing panels directly in run(), so the quiz game
logic, state machine (indexing, exhaustion tracking, next-round), and rendering
are all tangled together. The domain layer beneath is clean: answersToQuery,
queryQuizables, exhaustion counters, and field extraction via QuizablePanelConfig
all operate on plain Java objects and can be extracted intact.


Recommended approach: REST API + lightweight frontend
-----------------------------------------------------
Extract a QuizSession class (no Swing, no Thread) from the Quiz hierarchy,
keeping the indexQuizables() logic, exhaustion tracking, and answer verification.
Expose three endpoints:

  POST /api/quiz/start   { topic, answerType, queryFields, answerFields }
                         -> { sessionId, question }
  POST /api/quiz/answer  { sessionId, answer }
                         -> { correct, explanation, done }
  GET  /api/quiz/next    { sessionId }
                         -> { question }

"question" is a JSON tree mirroring what QuizablePanel renders from
QuizablePanelConfig. The field-path extraction already produces List<Object>
keys, so serialization to JSON is a small step. The frontend (React or vanilla
JS) renders question cards and answer choices from that JSON.


Main tradeoff
-------------
The hardest part is replacing QuizablePanel's reflection-based field rendering.
That panel walks field paths and renders text, images, and nested Quizable
references recursively. A server-side serializer must produce a typed tree:

  { type: "text",   value: "..." }
  { type: "image",  url:   "..." }
  { type: "nested", fields: [...] }

This essentially reimplements QuizablePanel's render logic as a JSON mapper.
Once it exists the frontend stays thin, but it is non-trivial work.

An HTMX/Thymeleaf approach (server-rendered HTML fragments) avoids that problem
— the server renders question HTML directly — but loses click-to-answer
responsiveness without a page reload. For a quiz game that is a real usability
hit, so the JSON API route is the better long-term investment.


Next steps
----------
1. Extract QuizSession from the Quiz hierarchy (domain logic, no Swing)
2. Build the Quizable field-tree JSON serializer
3. REST endpoints (Spring Boot / Javalin / Micronaut)
4. Minimal frontend for question rendering and answer clicks
